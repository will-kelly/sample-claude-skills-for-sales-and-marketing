# Launch asset specs

## Announcement blog post

Structure:

1. **Headline** — the outcome, not the feature name. "Deploy to AWS without storing access keys" beats "Introducing OIDC support."
2. **Opening (2–3 sentences)** — the problem, stated the way a customer would describe it
3. **What's new** — the feature, plainly
4. **How it works** — a short walkthrough with a code block, config snippet, or screenshot description
5. **Who it's for / use cases** — 2–3 concrete scenarios
6. **Availability** — plans, regions, GA vs. beta, what's not included yet
7. **Get started** — one CTA, usually docs

Offer 3 headline options. Keep the author byline as a placeholder.

## Customer email

- Subject line options: 3, under 50 characters, no clickbait
- Preview text: under 90 characters
- Body: under 150 words. Problem → what's new → one CTA.
- For existing customers, tell them whether they need to do anything (upgrade, enable a flag, nothing)

## Social posts

- **LinkedIn:** 80–150 words. Lead with the problem or a sharp observation, not "We're excited to announce." Line breaks for scannability. Link in the post or first comment depending on team practice — note it.
- **X / Bluesky:** under 280 characters. One idea per post. Developer audiences respond to a snippet or a GIF description more than to adjectives.
- Write variants with different angles (problem-led, outcome-led, "how it works"), not the same post reworded.

## Sales one-pager

Sections:

- **The one-sentence pitch**
- **Who to bring it up with** (personas, deal situations)
- **Discovery questions** (3) that surface the need
- **What it does / what it doesn't** — be explicit about limits
- **Competitive angle** — how it changes the conversation against the top 1–2 competitors
- **Objections and responses** (2–3)
- **Resources** — docs, demo, blog

## Internal FAQ

Write the questions sales, support, and customer success will actually get: pricing and packaging, availability by plan and region, migration or upgrade impact, known limitations, roadmap ("when will X be supported?" — give the approved answer or say "no committed date"), security and compliance implications.

## Release notes entry

- One line summary, then 2–4 lines of detail
- Link to docs
- Flag breaking changes clearly at the top

## Press release (Tier 1 only, and only if there's news)

Standard format: headline, subhead, dateline, lead paragraph with the news, a quote placeholder from an executive `[QUOTE: exec name, title — to be approved]`, a customer or partner quote placeholder, details, availability, boilerplate. Never fabricate quotes.
